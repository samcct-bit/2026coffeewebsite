# AI 草稿與人工發布流程

## 本次狀態

2026-10-23 已重新完成 49 項自動測試、草稿發布介面與手機版瀏覽器測試，以及 Firebase 自訂權杖登入／Worker 權杖驗證。部署前正式規則已讀回備份，教學集合權限未改動。本次依下列順序成套發布；完成後另記錄實際正式版本。

## 使用方式

1. 在烘焙資料庫按「AI 建立草稿」，或在編輯／即時烘焙表單按「儲存草稿」。生成內容不會直接改動首頁與單品頁。
2. 「草稿審核與發布」面板顯示目前公開版與待發布草稿，並標示各段風味字數。可按「編輯草稿」修訂內容。
3. 完成豆款身分、公開文案、AI 證據限制三項確認，選擇「風味參考・待杯測」或「本批杯測確認」。後者需要杯測日期。
4. 按「審核並發布」並再次確認，才會用交易更新公開快照。初韻、中調、尾韻各限 1～13 字，含頓號；超長不會偷偷截斷，須人工修訂。
5. 「捨棄草稿」不影響已發布版。新建而尚未發布的紀錄若捨棄，則移除該私有紀錄。
6. 「還原上一版為草稿」只建立草稿，仍須重新審核發布。下架刪除也會將當時公開版存入私有歷史；目前沒有歷史瀏覽器或已刪除紀錄的一鍵復原介面。

## 資料與權限

- coffee_roasts/{id}：公開快照，僅包含白名單欄位及發布資訊。已存在、沒有 publicationRevision 的紀錄視為舊版已發布，無須批次遷移。
- coffee_roast_drafts/{id}：管理員私有工作區。payload 保留原始紀錄、內部筆記、來源衝突及 AI 診斷；status 區分 draft／published。publishedPayload 用於捨棄草稿時保留管理員資料。
- coffee_publication_history/{id}/versions/{uuid}：管理員私有、不可由前端修改或刪除的歷史公開快照。使用 UUID 避免重建相同 ID 時覆寫舊歷史。
- 發布同時更新公開快照、私有狀態並歸檔上一版。交易會檢查草稿版本、公開版本與基準版，過期分頁不能覆寫、發布或捨棄較新資料。
- 規則要求發布內容的豆名、日期、三段風味與故事符合被審核草稿，並確認私有狀態同批交易轉為已發布。只有前端勾選狀態不會取得權限，仍須 Firebase 管理員身分。
- 舊版直接 setDoc 公開資料的寫入方式將被新規則拒絕；刪除仍限管理員。同專案的教學集合權限保留。

## 公開頁行為

- 新發布版依發布時間優先，不再被同名舊批次的 ROR 自訂分數壓過。
- 新發布單品一定使用動態 bean.html，不跳到同名但未同步的舊靜態頁。
- 新發布內容不使用硬編碼風味補寫；空值顯示未提供。未知 ID 顯示尚未發布／找不到，不代換另一款豆。
- 公開頁顯示風味依據；未杯測參考不展示數字杯測分數。實際杯測、AI 推測與品質認證仍需區分。
- 舊版已公開資料可能仍含先前的內部欄位；此次不自行批次清除。重新審核發布該筆資料時才套用白名單。

## AI 與編輯保護

- AI 服務失敗的離線參考會標示為 fallback，供人工判斷，不自動發布。
- 即時烘焙已有風味文字時不自動觸發 AI；手動重做前會確認。
- AI 生成期間若表單改變，結果不套用，避免較晚回來的請求蓋掉人工內容。
- 編輯存檔失敗保留表單，不把未確認成功的資料當成公開版。
- 新頁面使用 publication-v9 及新快取版本。已開啟的舊管理分頁必須重新整理。

## 部署順序

本次需前端與 Firestore 規則成套發布，不能只推送頁面讓正式站立即切版：

1. 保留目前正式規則與部署版本，重新核對同專案其他集合沒有改動。
2. 建立待發布正式環境版本，確認四個新增 JS 模組可載入、管理腳本與環境檔沒有公開。
3. 發布新 Firestore 規則並讀回確認，再立即升級已測試的網站版本。舊後台在這段短暫期間無法直接寫入；公開讀取不變。
4. 用專用測試紀錄驗證草稿私有、公開版穩定、發布交易、版本衝突、還原、匿名拒寫；清理測試紀錄。
5. 請管理員重新整理並登入，確認實際工作流程後記錄版本與結果。不以放開匿名寫入作回滾。

此次沒有改動 Cloudflare Worker，不需更換管理密碼或 Firebase 憑證。
